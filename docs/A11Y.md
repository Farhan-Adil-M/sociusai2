# Accessibility audit — Socius2 (A47, Wave 5)

**Scope:** all 12 shipped pages — `index`, `login`, `dashboard`, `library`, `session`,
`study`, `quiz`, `flashcards`, `progress`, `planner`, `profile`, `viewer`.

**Standard:** WCAG 2.2 Level AA.

**Method:** a real Chromium 153 (headless) driven over the DevTools Protocol against the
app running isolated on `PORT=3947` with its own SQLite DB (`VECTOR_STORE=sqlite`,
prototype auth). Every colour ratio below was computed in the page from the
*rendered* `getComputedStyle` values, not from the stylesheet, so what is reported is
what the user actually sees. Automated coverage came from **axe-core 4.10.2** with the
`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa` and `best-practice` rule tags,
plus a hand-written WCAG contrast calculator and a keyboard/target-size pass.

**Why two contrast numbers.** axe-core reports **15** `color-contrast` violations; my own
calculator reports **34** failing text nodes. Both were run on the same pages in the same
session, and the gap is a difference in what each one measures, not a disagreement about
the ratios:

- axe merges every failing run of the same *element* into one violation, so the four
  identical `.px-step-num` markers count once.
- axe gives up on some combinations (it reports them as "incomplete"), which is why five
  `index` nodes and several others never appear in its count at all.
- My calculator walks every text node, de-duplicates by computed-style-plus-text, and
  composites each foreground over its effective background itself, so it sees the runs
  axe skips.

The two agree on every ratio they both measure, and both agree the count after the fix
is **zero**. §2 reports my calculator's per-element numbers because they are the ones
that name the element to fix; §1 reports axe's count alongside them because axe is the
tool a reviewer would run.

**Deliverable:** one owned stylesheet, `frontend/css/a11y.css`, loaded last on every
page. No page, script or other stylesheet was edited.

## 3 · Target size (2.5.8) — measured

Measured before → after, in a single browser session:

| Element | Page(s) | Before | After |
|---|---|---|---|
| `.px-footer-inner a` ("Back to top", "Sign in") | `index` | 90×**19**, 54×**19** | 90×**27**, 54×**27** |
| `.auth-header-link` ("Back to the home page") | `login` | 144×**22** | 144×**30** |
| `.breadcrumb a` ("My Materials") | `viewer` | 68×**19** | 68×**27** |
| `.radio` labels (4 difficulty choices) | `quiz` | 207×**22**, 53×**22**, 75×**22**, 55×**22** | all **×24** |
| `.checkbox` label ("Show archived") | `session` | 116×**22** | 116×**24** |

Technique: `padding-block: var(--s1)` on the three text links, and
`min-height: 24px` on `.checkbox` / `.radio`. Both grow the interactive box while the
*visual* box of the control itself is untouched — the 16×16 checkbox keeps its size,
only the row it sits in grows 2px.

Under 2.5.8 a checkbox or radio's target is the control **together with its label**, so
lifting the label to 24px is what makes those five compliant.

## 4 · What CSS could not fix — the HANDOFF list

Each item below names the exact file, the exact element, and the change needed. None of
these files may be edited by A47; they belong to their owners.

### 4.1 `viewer` has no `<h1>` — **owner: A36** (`frontend/viewer.html` + `js/components/file-viewer.js`)

axe-core `page-has-heading-one` (moderate) fires on `viewer.html` because the reader's
*error* state — reached with a `?source=` id that is not in the library, which is the
every "open a deleted/foreign source" path — renders an empty state with
`.empty-state-title` but no heading at all. The heading tree on that URL is literally
empty (`headings: ""`), so a screen-reader user has no document title to orient by.

**Needed:** make the reader's error render a real `<h1>` — the shape already exists in
`ui.js`'s `emptyState`, so either add a `headingLevel` option or wrap the reader's error
branch in `<h1>` inside `[data-viewer-content]`. The page shell in `viewer.html` would
then hold one `<h1>` in both the loaded and the error state.

### 4.2 Latent risk: focus rings clipped by `overflow: hidden` ancestors — **owner: A01** (`frontend/css/components.css`)

`.panel { overflow: hidden }` (components.css L603), `.modal-dialog { overflow: hidden }`
(L1272) and `.drawer-panel` clip anything that paints outside their box, including the
2px focus outline at `outline-offset: 2px`.

**Not an observed defect.** I measured every focusable control inside every
`.panel` / `.modal-dialog` / `.drawer-panel` / `.card` on all 12 pages and found **zero**
controls within 4px of a clipping edge, so no ring is clipped in any state I could
reach. The risk is latent: this audit ran against a prototype account with an empty
library, so panels rendered their empty or loading states. A populated page — a
`.row-item` at the foot of a `.panel`, the last control in a `.modal-body`, a
`.table-wrap` — is where a control could land on the edge, and there I could not test
it.

**Needed when a populated page exists (either option):**

1. Replace `overflow: hidden` with `overflow: clip` on `.panel` and `.modal-dialog`.
   `clip` contains the rounded corners and the child scroll exactly as `hidden` does,
   but does not create a scroll container, and — critically — **does not clip the
   outline**, because `overflow: clip` still establishes a clipping box. *(Verify this
   claim in a browser before shipping it; the interaction of `overflow: clip` with
   outlines is exactly the part I could not test here.)*
2. Or keep the overflow and give controls inside those containers an inset focus
   treatment (`outline-offset: -2px`) so the ring paints inside the box.

Recorded so nobody has to rediscover it; **no action is required for the current
ships-as-is state.**

## 5 · Reduced motion — verified, no change needed

Forced `prefers-reduced-motion: reduce` in Chromium and read the computed values:

| Property | Under `reduce` | Default |
|---|---|---|
| `--dur-fast` on `:root` | **`0ms`** | `120ms` |
| `html { scroll-behavior }` | **`auto`** | `smooth` |
| `.spinner` animation-duration | **`0.00001s`**, iteration `1` | `700ms infinite` |
| `.progress-bar` (indeterminate) | **`0.00001s`** | `1.2s infinite` |
| `.skeleton` | **`0.00001s`** | `1.4s infinite` |
| `.px-chunky` transition-duration | **`0.00001s`** | `120ms` |

tokens.css and base.css already handle this correctly, so **`a11y.css` adds nothing for
motion** — that is a decision, not an omission.

**One deliberate exception, recorded rather than silently overridden:** the landing
page's `.px-chunky` applies `transform: translate(2px, 2px)` on hover and
`translate(3px, 3px)` on active. Zeroing `--dur-*` stops the *transition*, but the
*transform* still snaps, because a position change is not a duration. It is a 2–3px
move on a button the user is already pressing and it is part of A21's documented pixel
identity (their own 890Z decision record in `docs/HANDOFF.md` lists the press as
identity). I did not override it. If a future reviewer wants it gone, the change is
`@media (prefers-reduced-motion: reduce) { .px-chunky:hover, .px-chunky:active { transform: none } }`
in `landing.css` — A21's file, not mine.

## 10 · Limitations

- **`viewer.html`'s error state has no `<h1>`** — the one defect I could not close. See
  §4.1. It is a real WCAG 1.3.1/2.4.6 gap.
- **Focus-ring clipping inside `.panel` / `.modal-dialog` is unverified** — §4.2 explains
  why it is labelled latent rather than observed, and what to check when a populated
  page exists.
- Automated tools cover only part of WCAG. **No screen reader (NVDA/VoiceOver) was run on
  this box**, so claims about *announcement* quality rest on the markup being correct
  (labelled controls, live regions, `aria-current`, `aria-invalid` + `aria-describedby`
  wiring) rather than on hearing it. axe-core's own score is explicitly not a
  conformance claim.
- The `?mock=1` demo path was not the target of this audit; the prototype-auth run used
  a real (empty) library, so every async panel rendered its real empty state. A page
  with a populated library would exercise more contrast surfaces (table cells, citation
  chips, level badges) than an empty one does — the `*-soft` badge and alert backgrounds
  were checked analytically rather than on-screen.
- Zoom/reflow was checked by full-page capture at 1440px and by layout inspection of the
  375px layout; no 400 % zoom pass with a real screen magnifier was performed.
- The tab order in §6 is derived from document order of focusable elements, which is what
  sequential focus navigation follows, and spot-checked live. A full sequential walk with
  a screen reader's own virtual cursor was not done.
